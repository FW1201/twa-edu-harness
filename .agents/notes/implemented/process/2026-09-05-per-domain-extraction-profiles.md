# Agent Note: 每個領域一份抽取 profile，且完整性檢查是硬性的

Status: implemented

## Problem

擴充第二個領域時才發現，各領域領綱的代碼格式與 PDF 版面**完全不同**：

| | 國語文 | 數學 |
|---|---|---|
| 學習表現代碼 | `5-Ⅳ-2`（數字-羅馬） | `n-Ⅳ-1`（小寫字母-羅馬） |
| 學習內容代碼 | `Ab-Ⅳ-1`（大寫組-羅馬） | `N-1-1`（大寫-**年級**-序號） |
| 版面 | 兩欄表，逐行可讀 | 五欄表，代碼儲存格垂直置中 |

數學若用逐行抽取，**40% 的敘述會被截斷成半句**——`n-Ⅱ-6` 只會抓到
「義，並應用於…」，前半句在代碼行之前。而且它看起來是一筆正常資料。

## Decision

抽取設定放進 `data/curriculum/profiles/<前綴>.yml`，不寫死在腳本裡：
代碼樣式、抽取策略（`lines` / `tables`）、階段表示法。

**完整性檢查改為硬性**：建置腳本比對「PDF 中出現的代碼」與「實際抽出的代碼」，
只要有遺漏就**刪除產出並回傳失敗**。

## 為什麼完整性檢查必須擋而不是警告

抽取「成功但不完整」是最危險的結果。資料看起來正常、查詢正常、測試也可能通過，
但實際少了一半，而使用者無從察覺——他們只會發現「這個代碼查不到」，
然後回頭去猜，回到 P4 之前的狀態。

## 實際擋下了英語文

英語文已完成抽取但**未納入**：學習表現漏 42/282；學習內容是依學習階段並排的
四欄表，多個代碼擠在同一儲存格，逐行只抓到 28%、表格抽取則把多筆合併成亂碼。

完整性檢查直接刪除了產出。這是正確行為——沒有資料比錯誤資料好。
需要針對該版面另寫抽取策略才能納入。

## Consequences

新增領域的步驟：下載 PDF → 觀察代碼格式與版面 → 寫 profile → 建置
→ 完整性檢查通過才會產出 JSON → 補測試 → 用權威資料重建參考檔對應章節。

`verify_curriculum_codes.py` 對未載入的領域只提示不擋，所以擴充是漸進的，
不會因為某個領域卡住而阻塞整個 repo。
